- **Fixed (root cause confirmed by operator): random "tastele se opresc" freeze.** Symptom: only the physical keyboard stops sending input; Consumer/media keys keep working, RGB + nRF sleep blink fine. Operator pattern: keep typing fast → fine; pause ~5 s, then press ≥4 keys (e.g. `AWDVA`) → dead until power cycle.
- Cause: the one-shot `SET_REPORT(Output, NumLock)` "LED boot kick" in `keyboard_led_task()` (WirelessKeyboard.c ~2040-2063), fired ~300 ms after mount while EP 0x81 was already streaming at 1 kHz. The Sonix SN32 accepts an EP0 control transfer only while idle during enumeration; issued at runtime it poisons EP1 → ≤3 simultaneous keys OK, ≥4-key rollover = permanent freeze. Operator confirmed and noted the kick is redundant (SN32 lights NumLock by itself at power-up).
- Fix (Scenario A minimal, 2026-09-13): `#define KEYBOARD_LED_SYNC_ENABLED 0` + `if (!KEYBOARD_LED_SYNC_ENABLED) return;` at the top of `keyboard_led_task()`. Runtime early-return (not `#if`) so all helpers keep a reference and `-Wunused-function` stays quiet; `--gc-sections` then drops `tuh_hid_set_report` / `keyboard_led_build_output_report` / `tuh_hid_set_report_complete_cb` from the image entirely. Backup: `docs/WirelessKeyboard.c.bak-20260913-pre-led-kick-removal`. Built: `firmware/WirelessKeyboard_OTA.wkota` (73584 B payload, crc32=0xDF324607, image 816 B smaller).
- Recovery paths confirmed DEAD, so never assume a self-heal: `keyboard_halt_recovery_pending` is assigned only `false` (2873/3019/3063/3147) → CLEAR_FEATURE(ENDPOINT_HALT) never sent; `pio_usb_host_endpoint_reset_toggle()` returns `false` whenever the endpoint has a transfer armed (`Pico-PIO-USB/src/pio_usb_host.c:541-550`) and both call sites discard the result.
- `tuh_hid_set_default_protocol(HID_PROTOCOL_BOOT)` (`:3361`) DOES make TinyUSB emit SET_PROTOCOL(BOOT) on EP0 at every HID mount — operator ruled this normal and needed for keyboard init; not a regression.
- Second look-alike freeze mechanism (not fixed, no recovery exists): while `RADIO_AWAKE`, if the nRF SPIS stops arming MISO, `spi_write_frame` sees `slave_armed == false` for every frame, each burns `SPI_MAX_RETRIES` (8) then is dropped forever. Only evidence = `spi_frames_lost`/`spi_miso_retries`; the sole CSN reset pulse is in `radio_start_wake` (`:1408-1421`), reachable only from `RADIO_SYSTEM_OFF`, which itself needs a delivered `SYSTEM_OFF` frame. Candidate for a link-watchdog (Scenario B).
- Measured dead ends (do not re-investigate): each core has 2048 B stack (`.stack`/`.stack1` = 0x800), worst HID-mount chain ~1.1 KB (`parse_keyboard_led_output`=632, `parse_consumer_fields`=616), SDK installs an MPU stack guard → overflow = HardFault not silent corruption; no OOB write in queues/parsers. So the freeze was neither a stack overflow nor memory corruption.
- Open defects worth a follow-up (Scenario B): SPSC violation — producer (core 0) writes consumer-owned `usb_host_event_tail` on overflow while core 1 pop does read-modify-write (338-343 vs 361-370); reverse-ACK frame has no CRC and with `WIRELESS_KEYBOARD_OTA_SUPPORT=1` a corrupted MISO read routes into `dfu_process_command` (flash erase/program); `SPI_ACK_POLL_DFU_MS` defined but unused so the DFU poll has no rate limit (~6.6 kHz spin); `dfu_boot_report_task` spams 20 BOOT_OK frames every boot.
